# Codebase review

This review focuses on the current repository state and assumes **React Native New Architecture is the only supported target** going forward.

## What is working well today

- **Clear public API surface** via `/src/index.tsx`, with consistent exports for the main component set.
- **Strong theming foundation** in `/src/core` and `/src/styles/themes`, especially the Material Design 3 token model.
- **Healthy automated tests** in `src/**/__tests__`, with `yarn test` currently passing 56/56 suites.
- **Good contributor ergonomics** through `CONTRIBUTING.md`, issue templates, PR templates, and an Expo example app.
- **Documentation infrastructure already exists** in `docs/` and is a strong place to centralize architecture and maintenance guidance.

## Main weaknesses

### 1. New Architecture support is implicit, not explicit

Observed facts:

- The example app has `"newArchEnabled": true` in `/example/app.json`.
- The example Android project also enables the flag in `/example/android/gradle.properties`.
- The published package metadata and docs do **not** explain a New Architecture support policy.
- `src/components/Switch/Switch.tsx` reaches into `NativeModules.PlatformConstants`, which is exactly the sort of platform dependency that should be isolated when New Architecture is the only supported mode.

Why this matters:

- If the library is going to support New Architecture only, it needs a visible compatibility policy, targeted CI coverage, and explicit guardrails for architecture-sensitive code.
- Right now, support is inferred from the example app instead of stated as a product promise.

### 2. Several core components are too large and too coupled

Some representative files:

| File | Approx. size | Why it is a concern |
| --- | ---: | --- |
| `/src/components/BottomNavigation/BottomNavigationBar.tsx` | 1008 lines | Layout, state, animation, and navigation concerns are mixed together |
| `/src/components/Menu/Menu.tsx` | 715 lines | Positioning, portal behavior, animation, and visibility logic are tightly coupled |
| `/src/components/TextInput/TextInput.tsx` | 577 lines | Core API is split, but still heavy |
| `/src/components/TextInput/helpers.tsx` | 612 lines | Helper file has effectively become a second component |
| `/src/components/FAB/AnimatedFAB.tsx` | 628 lines | Complex animation code is concentrated in one module |
| `/src/components/FAB/FABGroup.tsx` | 553 lines | State machine and rendering are bundled together |

Why this matters:

- These are exactly the components showing up repeatedly in the upstream issue tracker.
- Large modules are harder to test behaviorally, harder to refactor safely, and more likely to regress during React Native upgrades.

### 3. The workspace versions are drifting

Observed facts:

- Root package: `react-native@0.82.1`, `react@19.1.1` in `/package.json`.
- Example app: `react-native@0.81.4`, `react@19.1.0` in `/example/package.json`.
- Docs app: `react@17.0.2` in `/docs/package.json`.

Why this matters:

- The example app is the main integration test bed, so version drift weakens confidence in upgrade safety.
- The docs workspace is naturally allowed to lag more than the example, but the gap still increases maintenance overhead and peer dependency noise.

### 4. Documentation is good for usage, thin for maintainers

Current strengths:

- There are solid getting-started and usage guides under `/docs/docs/guides`.
- The site is already wired for autogenerated component documentation.

Current gaps:

- No dedicated **architecture** guide.
- No **troubleshooting** guide for common Paper + React Navigation + Portal + theme edge cases.
- No **support matrix** documenting React Native, React, Expo, and New Architecture expectations.
- No **maintenance roadmap** explaining what the project is optimizing for next.

### 5. Test quality is stronger than test strategy

Observed facts:

- `yarn test --runInBand` currently passes.
- The suite includes 902 tests, but many component suites are very large:
  - `/src/components/__tests__/TextInput.test.tsx`: 1215 lines
  - `/src/components/__tests__/Button.test.tsx`: 934 lines

Why this matters:

- The project has meaningful test investment already.
- The next gain is not “more tests everywhere”; it is **better regression targeting** for architecture-sensitive flows: menu positioning, portals, text input overlays, accessibility semantics, and platform-version compatibility.

## Highest-leverage improvements

1. **Publish a New Architecture support policy**
   - Add one guide describing supported React Native / React / Expo ranges and what “supported” means.
   - Add CI jobs that run the example app configuration aligned with that policy.

2. **Refactor the largest interactive components first**
   - Start with `Menu`, `TextInput`, and `BottomNavigationBar`.
   - Extract positioning, animation, and measurement logic into tested helpers/hooks.

3. **Align the example app with the root package**
   - Keep the example on the same React Native major/minor as the root package whenever possible.
   - Treat example drift as a release-blocking signal.

4. **Add maintainer-facing documentation**
   - Architecture overview
   - New Architecture support matrix
   - Troubleshooting guide
   - Release checklist

5. **Shift from broad snapshot confidence to targeted behavioral confidence**
   - Prioritize tests for component reopening, overlay rendering, TalkBack/VoiceOver behavior, and React Native version upgrades.

## Recommended code-review lens for future changes

When reviewing new PRs, prefer the following questions over purely stylistic checks:

1. Does this change improve or weaken New Architecture clarity?
2. Does it increase coupling inside already-large components?
3. Does it add or protect a behavior that is known to regress in the issue tracker?
4. Does the example app exercise the change in a realistic way?
5. Does the documentation explain how consumers should use or migrate the feature?
